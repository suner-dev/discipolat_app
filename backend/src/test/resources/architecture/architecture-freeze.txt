# EXCEPTION CONSTATEE ET REGELEE - 2026-10-12 (a ne pas reproduire).
# R1 est passe de 7990 a 8009 (+19) avec le commit 44907763 (abonnement SaaS MTN MoMo, T6.3) :
# SaasMomoSubscription est une entite JPA posee dans payments/domain, et MomoSubscriptionService
# (domaine) importe des repositories d'autres contextes, HttpClient et Jackson. C'est le motif
# deja gele 7990 fois, pas une nouvelle categorie d'impurete. Le re-gel est choisi parce que
# deplacer l'entite ne retirerait rien : le service appellerait toujours les repositories, R1
# resterait enfreint ; la correction reelle est la separation domaine/infrastructure du contexte
# payments (migration V1), pas un renommage de paquet. Ce re-gel est trace dans KNOWN_ISSUES.
#
# EXCEPTION CONSTATEE ET REGELEE - 2026-10-13 (3e du jour, apres les deux autres).
# R1 est passe de 8009 a 8011 (+2) avec le rattrapage d'une adhesion approuvee dont
# le lien d'activation a expire (V253) : `TenantJoinRequest` a recu deux colonnes,
# `invitation_id` et `invitation_sent_at`, donc deux annotations `@Column`.
# Ce n'est PAS une nouvelle categorie d'impurete : `TenantJoinRequest` est deja
# signalee comme entite JPA posee dans `domain` (son `@Entity` et son `@Table`
# sont dans les 8009). On ne peut pas ajouter une colonne sans `@Column` — c'est
# la definition meme d'une colonne JPA. La seule facon de ne pas crever ce
# plafond serait de renoncer a memoriser le lien, c'est-a-dire de laisser
# l'adhesion approuvee devenir introuvable et non relancable : echanger un plafond
# de dette contre un cul-de-sac pour l'utilisateur n'est pas un nettoyage.
# La correction reelle reste la sortie des entites du domaine (migration V1), comme
# pour les 8009 precedentes.
#
# EXCEPTION CONSTATEE ET REGELEE - 2026-10-13 (a ne pas reproduire).
# R4 est passe de 3010 a 3013 (+3) avec le correctif de l'inscription « au nom d'une
# eglise » (faille JoinMode) : `TenantJoinService.registerWithSlug` porte `@Transactional`,
# ce qui compte 3 entrees R4 (Transactional + Propagation + Isolation).
# Ce n'est pas une nouvelle categorie d'impurete : la classe voisine possede deja
# 5 methodes `@Transactional` gelees pour la meme raison (`join`, `joinBySlug`,
# `registerWithCode`, `approveRequest`, `pendingRequests`). Retirer l'annotation
# serait un REGRESSION fonctionnelle et non un nettoyage : la methode ecrit une
# demande de rejointure puis notifie les responsables, et sans transaction un
# echec au milieu laisserait une demande tracee sans l'email correspondant (et
# l'inverse). La correction reelle reste la sortie des annotations de conteneur du
# domaine (migration V1), pas un amenagement local.
# La dette n'augmente que parce que la porte est enfin FERMEE : c'est le prix,
# assume et borne, de l'application du JoinMode a l'inscription par lien.
#
# EXCEPTION CONSTATEE ET REGELEE - 2026-10-13 (2e du jour, apres la precedente).
# R4 est passe de 3013 a 3022 (+9 = 3 methodes transactionnelles x 3 entrees
# : Transactional + Propagation + Isolation) avec le rattrapage d'une adhesion
# approuvee dont le lien d'activation a expire :
#   1. `TenantJoinService.resendInvitationForRequest` — ECRIT (relance le jeton,
#      horodate la demande, journalise). Sans transaction, une relance partie a
#      moitie laisserait un jeton invalide en base alors que l'ecran annonce un
#      email envoye : c'est-a-dire un lien que PERSONNE ne peut ouvrir, affiche
#      comme valide. Exactement le piege qu'on ferme ici.
#   2. `InvitationService.reissue` — ECRIT (nouveau token_hash, expiration,
#      remise a zero de reminded_at). Memes raisons.
#   3. `TenantJoinService.joinRequests` — LECTURE. `readOnly = true` n'est pas
#      cosmetique : Hibernate passe en FlushMode.MANUAL et evite le dirty
#      checking sur des listes d'ecrans d'administration.
# Aucune de ces trois methodes n'est supprimable sans regression. Meme motif que
# les 7 methodes `@Transactional` deja gelees dans `TenantJoinService`, et que
# les 3013 entrees deja gelees ailleurs : la dette R4 est un constat V0.1 dont la
# resolution est la sortie des annotations de conteneur du domaine (migration V1).
#
# Piege explicite pour le prochain : `pendingRequests` delegue a `joinRequests`,
# mais son `@Transactional` NE PEUT PAS etre retire. L'appel interne est une
# auto-invocation : le proxy Spring ne s'applique pas, donc c'est l'annotation du
# delegateur qui ouvre la transaction. La retirer laisserait les lectures sans
# transaction — un piege classique, invisible a la compilation et aux tests
# unitaires.
#

# R1 8011 -> 8025 (+14) et R4 3022 -> 3028 (+6) avec la recherche filtrable
# des prieres (statut « exaucée » + totaux par categorie/priorite, correction

#   1. `PrayerRepository.searchFiltered/countGroupByStatut/countGroupByCategorie/
#      countGroupByPriorite` — methodes `@Query` portees par la meme interface
#      deja gele 8011 fois : ajouter une requete ne cree pas une nouvelle
#      categorie d'impurete, cela ajoute 2 a 3 entrees R1 par methode (Query +
#      QueryRewriter + Pageable/Page) la ou la signature les impose.
#   2. `PrayerService.searchFiltered/stats` — memes motifs que les methodes
#      transactionnelles voisines deja gelees : `@Transactional` (x3 entrees
#      R4) et Pageable/Page traversent la couche application (x2 entrees R1).

# (migration V1), comme pour les 8011 precedentes.
